# 三方压缩系统实测对比（2026-10-26）

## 实验设置

| 项目 | 设置 |
|---|---|
| 对话 | 131 条消息，约 **9,087 tokens**（含 120 条干扰日志 + 11 个金标事实） |
| 压缩模型 | 同一个本地端点 `tierflow_pro`（OpenAI 兼容，127.0.0.1:8330） |
| 评测 reader | 同一模型，4 个问题，按"最短精确短语"评分（已做反引号/标点归一化） |
| OpenClaw | 从 `openclaw 2026.10.5` 的 `agent-core` 提取真实 prompt（`SUMMARIZATION_SYSTEM_PROMPT` + checkpoint 分节）与切点策略（`keepRecentTokens`，测试中按对话规模缩放为 `min(4000, total/2)`），用同一模型执行 |
| Hermes | 本地 Hermes 安装的**真实** `ContextCompressor`（venv 内运行，辅助 LLM 调用替换为同一端点；threshold=0.5、protect_last_n=20、tail_mode=legacy） |
| NeverFull V11 | 本仓库流水线：状态快照 + 折叠占位符（digest + ref）+ 分节摘要 + 证据探针 + 保留最近 6 轮原文 |

指标：压缩率（1 - 压缩后/压缩前 token）、证据保留（11 个金标 span 的命中比例）、状态一致性（被编辑的 config 是否标记为当前/过期）、4 题问答、压缩耗时、压缩调用 token 成本。

## 结果

| system | compression | evidence recall | stale | QA | latency | cost tokens |
|---|---|---|---|---|---|---|
| openclaw | 0.491 | 0.636 | 0.5 | 0.75 | 18.3s | 8,934 |
| hermes | 0.471 | 0.636 | 1.0 | 0.75 | 67.7s | 11,410 |
| **neverfull** | **0.860** | **1.000** | **1.0** | **1.00** | 25.5s | 9,369 |

### 问答明细

| 问题（期望） | OpenClaw | Hermes | NeverFull |
|---|---|---|---|
| 用了什么存储（sqlite） | ✅ | ✅ | ✅ |
| 哪个路径前缀不能改（/api/v1） | ✅ | ✅ | ✅ |
| 复现失败测试的命令（pytest -q） | ❌ 摘要里没有 | ❌ 摘要里没有 | ✅ 折叠 digest 的 `[COMMANDS]` 保住 |
| 待办任务（migrate config.yaml） | ✅ | ✅ | ✅ |

> 初版评分把 OpenClaw 的第 4 题误判为 MISS（答案带反引号），归一化后修正为 0.75。

## 解读

1. **证据保留**：三种方案都保住了决策和路径（sqlite、/api/v1），但**只有 NeverFull 保住了命令**。OpenClaw 与 Hermes 的自由文本摘要都把 `pytest -q` 丢了——这是 KEEP-Bench 说的"QA 碰巧答对但证据链已断"的典型：命令不在上下文里，后续 agent 无法复现测试。
2. **状态一致性**：被编辑过的 `config.yaml`，OpenClaw 的摘要只写了"updated"，没有标记旧读取已过期（stale=0.5）；Hermes 和 NeverFull 都保留了版本状态（1.0）。NeverFull 是靠结构化状态表硬保证的，Hermes 是靠摘要里保留"updated"。
3. **压缩率**：NeverFull 0.86 最高，因为它有结构化折叠 + 摘要 + 6 轮原文，信息密度高；OpenClaw/Hermes 都在 0.47–0.49，因为各自保留了较大的原文尾巴（OpenClaw ~4k tokens、Hermes 20 条消息）。
4. **成本与延迟**：OpenClaw 最便宜最快（8.9k tokens / 18s）；NeverFull 成本几乎持平（9.4k / 25s，多了一次探针与折叠计算，但没有额外 LLM 调用）；**Hermes 最贵最慢（11.4k / 68s）**——它的压缩链路在 9k token 的会话上做了多轮辅助调用和开销较大的预处理，且固定 20 条尾巴让收益变小。
5. **一句话**：在这次小规模长会话上，**NeverFull 的"证据保留 + 状态一致"明显最好，成本与 OpenClaw 持平；OpenClaw 便宜快但会丢命令；Hermes 保状态但在这个规模上性价比最差**。

## 局限（必须说清）

- 单一合成对话、4 个问题、单次运行；结论是方向性的，不是统计显著的排名。
- OpenClaw 是**按 v2026.10.5 源码复刻的 prompt + 切点策略**，不是在 Gateway 进程里跑的真实会话；其 `keepRecentTokens` 为适配测试规模做了缩放（默认 20k）。
- Hermes 是真实压缩器，但辅助 LLM 被替换为同一本地端点（正常运行时它可能走单独的廉价模型）。
- Reader 用的是同一个本地模型，4 题里 3 题所有系统都能答对，区分度主要来自"命令"和"待办"两题。
- 成本是 `usage.prompt_tokens + completion_tokens` 的实测值；未计缓存与网络开销。
