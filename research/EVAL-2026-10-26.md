# 记忆基准评测：LoCoMo（补充）

生成日期：2026-10-26

## 动机

此前的三方对比基于一条 131 条消息的编码会话，只能说明“编码任务上的证据保留”。本评测补上公开记忆基准 **LoCoMo**（snap-research/locomo，10 条长对话、约 200 问/条，含时间推理与对抗题），检验压缩后的长对话是否还能回答事实性问题。

## 方法

- 数据：`benchmark/data/locomo10.json`，取 `conv-26`；按类别分层抽 5 个问题（类别 1–5）。
- 视图（同一对话、同一摘要模型 `tierflow`）：
  - `full`：全部会话原文（含 `[Session N — date]` 头）；
  - `truncate`：保留末尾 35% 字符；
  - `llm`：通用摘要 + 最近一次会话原文；
  - `v11`：状态快照（含每会话日期）+ 折叠 digest + `[EVIDENCE]` 事实表 + 显著原文行 + 分节摘要 + 最近会话原文。
- 指标：压缩率（1 − 视图 token / 原文 token）、证据保留（金标 dia_id 内容的 3-gram 存活率）、问答准确率（本地 LLM reader，精确匹配或 token-F1 ≥ 0.5）。
- Reader 提示要求用会话头解析 “yesterday / last week” 等相对时间。

## 结果（conv-26，5 问）

| 策略 | 压缩率 | 证据保留 | 问答准确率 | 摘要耗时 | 摘要 tokens |
|---|---|---|---|---|---|
| full | 0.000 | 1.000 | 0.600 | 0 s | 0 |
| truncate | 0.650 | 0.900 | 0.200 | 0 s | 0 |
| llm（通用摘要） | 0.981 | 0.400 | 0.000 | 9.4 s | 17,166 |
| **v11（折叠 + 事实表 + 分节）** | **0.920** | **0.900** | **0.200** | 11.3 s | 17,547 |

## 解读

1. **通用 LLM 摘要在 98% 压缩下丢掉 60% 的证据**（0.400）。这正是 KEEP-Bench 指出的“摘要看起来合理，但证据链已断”。
2. **V11 在 92% 压缩下把证据保留拉回 0.900**，与 35% 截断持平，但压缩率高 27 个百分点。关键不是摘要写得更好，而是 `[EVIDENCE]` 事实表与显著原文行是**原样保留**的，不依赖模型复述。
3. **问答准确率仍偏低**：完整上下文也只有 0.600，说明本地 reader 对 LoCoMo 的时间推理/多跳问题能力有限；压缩视图 0.200 主要受 reader 上限约束，不能直接解读为“压缩导致答错”。要得到可信的 QA 结论，需要更强 reader 或更大样本。
4. **会话日期头是关键**：早期试验中通用摘要丢失 `[Session N — date]`，相对时间无法解析，QA 全 0；V11 的状态快照保留每会话日期，因此没有这个问题。

## 局限

- 单条对话、5 个问题，样本量不足，结论是方向性的。
- 尝试扩展到 2–3 条对话时，本地模型端点对长摘要请求频繁超时/502，运行被中止；这是评测环境问题，不是脚本失败（`benchmark/memory_eval.py` 已内置重试与超时）。
- QA reader 是本地小模型，LoCoMo 的类别 2（时间）与类别 5（对抗）对它是强项之外的题型。
- 证据保留用 3-gram 存活率，对同义改写不友好；它偏向原样保留的策略（V11/截断），这正是本评测想测的维度。

## 复现

```bash
python benchmark/memory_eval.py \
  --data benchmark/data/locomo10.json \
  --convs 1 --questions 5 --reader llm \
  --json research/data/memory_eval.json \
  --markdown research/EVAL-2026-10-26.md
```

确定性子集（无 LLM，可进 CI）：

```bash
python benchmark/memory_eval.py --reader extractive --questions 3 --strategies full,truncate
```
